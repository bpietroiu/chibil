# quickjs-api-consumer

A C# program that evaluates JavaScript (`40+2` → `42`) through `quickjs.Api` — a
facade class that **chibil** generated by compiling QuickJS's C to MSIL. No
reflection, no hand-written P/Invoke: the consumer calls real C functions
(`JS_NewRuntime`, `JS_Eval`, `JS_ToInt32`, …) as ordinary managed methods.

The referenced `qjs.dll` is linked against a **managed musl** (musl libc compiled
to MSIL) running on the **managed PAL** (`Chibil.Pal` — the Linux syscall seam
implemented over portable .NET APIs: `Console`, `NativeMemory`,
`RandomNumberGenerator`). The result has **zero native dependencies**, so it runs
and debugs identically on Windows, Linux and macOS.

## Run / debug in Visual Studio (Windows)

1. Open **`qjsconsumer.slnx`** in Visual Studio (2022 17.10+ or 2026).
2. Right-click **qjsconsumer** → *Set as Startup Project* (if it isn't already).
3. Press **F5**.

Expected output:

```
JS_ToInt32=42  JSValue.u.int32=42  tag=0
BEHAVIORAL_ORACLE_OK: quickjs.Api.JS_Eval("40+2") == 42
```

Breakpoints in `Program.cs` work out of the box. `Chibil.Pal` is a
`ProjectReference`, so VS builds it, copies it next to the consumer, and lists it
in `qjsconsumer.deps.json` (the loader needs it because `qjs.dll`'s `<Module>`
`.cctor` calls `__chibil_pal_init`).

> Command-line equivalent: `dotnet run -c Debug` from this directory.

### Stepping into the QuickJS / musl C source

`qjs.dll` is built `-g` and carries an **embedded Portable PDB** with sequence
points mapping IL back to the original `.c` files (`quickjs.c`, `dtoa.c`,
`mmap.c`, the mallocng allocator, …). You can step *into* the C code from
`Program.cs`.

The PDB stores **bare file names** (the build compiles each TU from its own
directory under WSL), so the first time VS stops in a C frame it will ask for the
file. Point it at:

- QuickJS engine: `..\quickjs-2025-09-13\` (e.g. `quickjs.c`, `cutils.c`)
- musl libc: `..\musl-1.2.6\src\` (e.g. `malloc\mallocng\malloc.c`, `mman\mmap.c`)

VS remembers the directory, so subsequent files in the same tree resolve
automatically. (Tools → Options → Debugging → *Require source files to exactly
match the original version* can be unchecked if the checksum prompt is noisy.)

## Rebuilding `qjs.dll`

`qjs.dll` is a build artifact (git-ignored, third-party source tree). Regenerate
it after changing QuickJS, the managed musl, the PAL, or the linker —
cross-platform, no WSL:

```
dotnet build targets/quickjs/QuickJsManaged.proj
```

This compiles the QuickJS engine TUs against the managed-musl headers, links them
with the managed-musl objects + `Chibil.Pal` (binding `__chibil_syscall`/
`__chibil_get_tp` to the PAL), and copies the fresh `qjs.dll` to
`..\quickjs-2025-09-13\qjs.dll` (this project's `HintPath`). The managed-musl object
set is built by `targets/managed-musl/ManagedMusl.proj`. To do everything in one
step (toolchain + musl + qjs.dll + run this consumer as an oracle):
`dotnet build build.proj -t:QuickJs`.

## Native-libc oracle (Linux only)

A separate validation links `qjs.dll` against the *real* libc via P/Invoke and
runs the same oracle on Linux: `wsl bash targets/build/quickjs-api-run.sh`. That
path does not use the PAL and only runs on Linux.
